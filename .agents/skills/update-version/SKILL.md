# 更新版本

用户维护带有私有改动的 T3 Code fork。“更新版本”授权执行本地上游同步、冲突修复及必要的合并提交。默认更新当前 worktree 的当前分支；不要自行切换到 `main`，也不要以纯上游代码替换 fork。

## 确认仓库与上游

1. 阅读当前 checkout 的 `AGENTS.md`。检查 `git status --short --branch`、`git branch --show-current`、`git remote -v`、`git worktree list` 和现有 stash，记录起始 HEAD 与工作区状态。
2. 若已有 merge、rebase、cherry-pick、revert 或未解决冲突，不接管或中止用户的操作；说明现状并询问如何继续。detached HEAD 且未指定目标分支时，先确认目标。
3. `origin` 是用户的 fork，不能把 `git pull origin` 当作更新上游。保留现有远程配置和分支跟踪关系。
4. 若缺少 `upstream`，本项目 README 与 CONTRIBUTING 指向的官方仓库是 `https://github.com/pingdotgg/t3code.git`。核对当前项目仍对应此仓库后，执行 `git remote add upstream https://github.com/pingdotgg/t3code.git`。若已有 `upstream`，使用其配置；地址与项目来源矛盾时先核实，不擅自改写。
5. 用户指定上游分支时使用该分支，否则通过 `git ls-remote --symref upstream HEAD` 查询远端默认分支，不硬编码 `main`，也不只依赖可能过期的 `upstream/HEAD`。获取失败或来源不明确时停止合并，不能用缓存引用声称已更新到最新。
6. 用明确 refspec 获取该分支，例如 `git fetch upstream refs/heads/<分支>:refs/remotes/upstream/<分支>`，然后记录其完整 SHA。后续以此 SHA 为本次目标，避免引用变化影响合并。这里只更新源码，不自行改版本号、安装发行包或升级无关依赖。

## 保存本地工作

1. 比较目标 SHA 与本地 HEAD 的共同祖先和双方独有提交，检查 fork 的差异及未提交修改，识别需要保留的私有行为。若目标已经是 HEAD 的祖先，报告已包含此次获取的上游代码，保留工作区原状，不制造合并或 stash。若历史因浅克隆不完整，先补齐；仍无共同祖先时停止，不使用 `--allow-unrelated-histories` 强行合并。
2. 合并前创建唯一的本地备份分支，例如 `backup/pre-upstream-<时间戳>`，指向起始 HEAD；不覆盖已有分支。将起始分支、HEAD、目标 SHA、状态、暂存区与工作区的二进制 diff 保存到工作树外的私有备份目录。备份分支只保存已提交代码，不能代替未提交内容的备份。
3. 工作区有修改时，先保存未跟踪文件副本，再执行带唯一说明的 `git stash push --include-untracked -m <说明>`，记录本次新建 stash 的确切对象 SHA，并核对其中包含的暂存、未暂存和未跟踪内容。确认工作区已适合合并后继续；stash 未成功保存的内容不能清理。不要使用 `--all` 搬走忽略文件、依赖或运行数据。
4. 备份完成后不再以易变化的 `stash@{0}` 指代本次备份。保留用户原有 stash；不使用 `stash clear`、`reset --hard`、`clean -fd` 或强制检出来腾空工作区。若发现其他会话在此期间修改了 HEAD 或文件，先协调，不能覆盖并发工作。

## 合并与解决冲突

1. 默认使用 merge 保留 fork 的提交历史，不自动 rebase。能快进时执行 `git merge --ff-only <目标SHA>`；双方分叉时执行 `git merge --no-ff --no-commit <目标SHA>`，检查合并结果后完成本地合并提交。
2. 有冲突时，逐文件读取共同祖先、本地版本、上游版本及关联调用方或测试。保留私有功能的意图，同时适配上游的新接口、目录和行为；不要对整个文件或整个合并机械选择 `ours`、`theirs`、`-X ours` 或 `-X theirs`。
3. 文本无冲突也要检查语义兼容性，尤其是本地定制与上游同时涉及的契约、状态逻辑和入口。上游已实现的等价功能可复用；不要因为出现冲突就删除私有功能。依赖清单先合并意图，再按项目包管理器重新生成必要的锁文件，避免手拼生成文件。
4. 只有无法从代码、测试和用户要求判断的产品取舍才询问用户；说明具体冲突、可选方案和影响。普通代码冲突自行修复，不因“存在冲突”直接结束任务。
5. 只暂存本次合并和冲突修复所需的文件，确认 `git ls-files -u` 为空并检查暂存 diff，再完成合并提交，例如 `chore: merge upstream changes`。完成这一步后再恢复原未提交工作，避免把用户的草稿混入合并提交。
6. 如创建过 stash，用记录的 SHA 执行 `git stash apply --index <stashSHA>`，恢复原暂存状态和工作区内容。不要用 `pop`；保留该备份直至用户决定清理。若恢复发生冲突或未跟踪文件同名，检查已恢复内容后逐项整合，不盲目重复 apply 或覆盖文件。必要时从备份提取内容，尽量恢复原暂存边界，并明确报告无法原样恢复的部分；原本未提交的工作继续保持未提交。

## 验证与交付

- 在合并和本地改动恢复完成后验证。确认目标 SHA 是当前 HEAD 的祖先，原有私有提交仍在历史中，无未解决冲突，并用备份逐项核对私有改动及未跟踪文件的去向。`git diff --check` 与暂存区检查通过不能替代行为验证。
- 按当前 `AGENTS.md` 执行与冲突修复、私有功能受影响范围对应的测试和包级检查；必要时运行 `vp run check:changed <起始HEAD>`，避免相对旧 `origin/main` 扩大检查范围。不运行仓库禁止的全量检查。依赖确需安装时遵循 setup 标记与 `vp i` 流程。
- 修复同步引起的回归；区分原有失败和本次新失败，不能通过删除测试或私有功能让检查变绿。前端、协议或 provider 相关修复按项目要求检查相关入口、客户端与连接方式。浏览器或电脑操作仍需用户明确授权，未执行时如实标注。
- 不推送远程、不创建 PR、不安装或重启当前 T3 Code，也不修改 `~/.t3/userdata`；这些动作需要单独的用户指令。不要为测试停止用户正在使用的服务。
- 获取失败、无法判断的行为冲突或验证失败时，保留恢复点，明确已完成阶段和当前状态；不要自动丢弃改动或声称更新完成。继续完成可独立处理的部分。
- 最终简要报告：上游地址与分支、更新前后短 SHA、合并方式、私有改动如何保留、冲突处理结果、验证结果及未验证范围、备份分支和本次 stash SHA（若有）。源码更新与已安装客户端更新要明确区分。
